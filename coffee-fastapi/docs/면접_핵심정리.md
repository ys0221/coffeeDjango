## 1. 알아야 할 것

### 수준 구분

면접에서 코드를 한 줄씩 설명하라고 하는 경우는 드물어요. 대신 **"왜 그렇게 했는지", "어떻게 동작하는지"를 말로** 설명할 수 있는지를 봐요.

| 표시 | 수준 | 의미 |
|---|---|---|
| 🟥 | 반드시 설명 | 안 보고 말로 설명할 수 있어야 함. 그림이 필요하면 손으로 그릴 수 있어야 함 |
| 🟧 | 개념 설명 | 무엇이고 왜 쓰는지 한두 문장으로 말할 수 있으면 됨 |
| ⬜ | 몰라도 됨 | 물어보면 "문서를 보고 설정했다" 정도로 답해도 됨 |

### 1-A. FastAPI 전환에서 알아야 할 것

**🟥 ① Spring과 같은 계층 구조**

FastAPI로 바꿔도 **구조는 그대로**고, 각 계층을 부르는 이름과 문법만 다르다.

```text
Spring:   Controller → Service → Repository → DB
FastAPI:  Router     → Service → Session    → DB
```

| 역할 | Spring Boot | FastAPI |
|---|---|---|
| 요청 받기 | `@RestController` | `APIRouter` + `@router.get` |
| 요청/응답 양식 | DTO + `@Valid` | Pydantic 모델 |
| 테이블 | `@Entity` (JPA) | `Base`를 상속한 모델 (SQLAlchemy) |
| DB 작업 | Repository + EntityManager | Session (Repository가 따로 없음) |
| 비즈니스 로직 | `@Service` 클래스 | 함수만 모아둔 파일 |

> 💬 "Spring의 Controller, Service, Repository 구조를 그대로 옮겼고, Python에서는 Router, Service 함수, SQLAlchemy 세션이 각각 그 역할을 합니다."

**🟥 ② Spring과 FastAPI의 핵심 차이 3가지**

| | Spring Boot | FastAPI |
|---|---|---|
| **의존성 주입** | 앱이 시작될 때 Bean을 만들어 생성자로 주입 | 요청이 올 때마다 `Depends(함수)`로 주입 |
| **트랜잭션** | `@Transactional`이 commit/rollback을 자동 처리 | `db.commit()` / `db.rollback()`을 직접 작성 |
| **입력 검증** | `@Valid`를 붙여야 검증 | Pydantic 타입만 선언하면 자동 검증 (실패 시 422) |

> 💬 "가장 큰 차이는 트랜잭션이었습니다. Spring은 `@Transactional`이 숨겨서 처리해 주지만, FastAPI에서는 commit과 rollback을 직접 써야 해서 오히려 트랜잭션 경계를 더 명확히 이해하게 됐습니다."

**🟥 ③ 주문 트랜잭션과 개선한 점**

```python
try:
    for product_id, quantity in items:
        product = db.get(Product, product_id)
        product.decrease_stock(quantity)   # 재고 부족이면 에러
        db.add(Order(...))                 # 아직 DB에 반영 안 됨
    db.commit()                            # 전부 성공 → 한 번에 반영
except Exception:
    db.rollback()                          # 하나라도 실패 → 전부 취소
    raise
```

- **기존 Spring 코드의 문제:** 컨트롤러에서 상품마다 트랜잭션을 따로 열어서, 여러 상품 중 하나가 재고 부족이면 **일부만 주문**됨
- **개선:** 주문 전체를 하나의 트랜잭션으로 묶어서, 하나라도 실패하면 **전부 롤백**
- 테스트(`test_order_out_of_stock_rolls_back`)로 확인

> 💬 "기존 코드를 옮기다가 여러 상품을 주문할 때 일부만 저장될 수 있는 문제를 발견해서, 주문 전체를 하나의 트랜잭션으로 묶어 하나라도 실패하면 전부 롤백되게 고쳤습니다."

**🟧 ④ 세션 = 영속성 컨텍스트, 요청마다 하나**

```python
def get_db():
    db = SessionLocal()    # 요청이 오면 새 세션 생성
    try:
        yield db           # 라우터 함수에 빌려줌
    finally:
        db.close()         # 응답 후 반드시 닫기
```

- 세션 = JPA의 영속성 컨텍스트. 한 요청의 DB 작업을 모아서 관리 (1차 캐시, 변경 감지, commit/rollback)
- `Depends(get_db)`로 **요청 1개마다 세션 1개** → 요청끼리 데이터가 섞이지 않음

> 💬 "`Depends`와 `yield`로 요청마다 세션을 열고 닫게 해서, Spring이 요청 단위로 영속성 컨텍스트를 관리하는 것과 같은 구조를 직접 구성했습니다."

**🟧 ⑤ 기본 CRUD는 세션이 제공, 조건 조회는 직접 작성**

| Spring (JpaRepository) | SQLAlchemy (Session) |
|---|---|
| `findById(id)` | `db.get(Product, id)` |
| `findAll()` | `db.scalars(select(Product))` |
| `save(p)` | `db.add(p)` + `db.commit()` |
| `findAllByCustomerEmail(email)` (메서드 이름으로 자동 생성) | `select(Order).where(Order.customer_email == email)` (직접 작성) |

**🟧 ⑥ 에러 처리**

- 서비스에서 `raise NotFoundError(...)` (= `throw new ...`)
- `main.py`의 `@app.exception_handler`가 잡아서 404, 400 응답으로 변환 (= `@RestControllerAdvice`)

**⬜ 몰라도 되는 것**

- `check_same_thread`, `autoflush`, `expire_on_commit` 같은 SQLAlchemy 세부 설정
- `Mapped[int]`, `mapped_column` 같은 모델 정의 문법
- `yield`, 리스트 컴프리헨션, `**kwargs` 같은 Python 문법 세부

### 1-B. Claude Tool Use에서 알아야 할 것

**🟥 ① 전체 흐름 (손으로 그릴 수 있어야 함)**

```text
손님: "Ethiopia 2개 주문해줘"
  ↓
서버 (FastAPI /chat)
  ↓
[반복, 최대 8번]
  ① Claude에게 전송: 대화 전체 + Tool 목록 + 규칙
  ② stop_reason 확인
     - tool_use → 서버가 Tool 실행 (DB 검색, 주문)
                  → 실행 결과를 대화에 붙여서 ①로
     - end_turn → 최종 답변 → 반복 종료
  ↓
손님: "주문 완료! 16,000원"
```

- **Claude는 실행을 요청만 하고, 실제 실행은 우리 서버가 한다** (Claude는 DB에 직접 접근하지 않음)
- 손님 메시지 1번에 Claude 호출은 "Tool 사용 횟수 + 1"번

**🟥 ② Claude는 기억하지 못한다 (stateless)**

- 매번 대화 전체(`messages`)를 다시 보내야 함
- 그래서 **판단에 필요한 맥락을 빠짐없이 전달**해야 함 → 시나리오 6에서 실제로 문제 발견

**🟥 ③ AI Agent란**

> 개발자가 LLM에게 **행동 규칙, 도구(Tool), 반복 구조**를 제공 → LLM이 스스로 판단해서 도구로 일을 수행하고, **그 결과를 보고 다음 행동을 정하며** 목표를 끝까지 처리하는 것

| 우리가 준 것 | 코드 | 역할 |
|---|---|---|
| 행동 규칙 | `SYSTEM_PROMPT` | 추측 금지, 주문 전 확인 |
| 도구 | `TOOLS` + 실행 함수 | 검색, 주문, 주문 조회 |
| 반복 구조 | `agent.py`의 반복문 | 결과를 보고 다시 판단할 기회 |

- 일의 순서(검색 → 주문)는 **개발자가 코드로 정하지 않고 LLM이 판단**
- **챗봇 vs Agent:** 챗봇은 말로 답하고 끝남. Agent는 Tool로 실제 일을 하고(DB 재고가 실제로 줄어듦), 결과를 보고 다음 행동을 정함

**🟥 ④ 안전장치**

| 장치 | 막는 것 | 확인한 시나리오 |
|---|---|---|
| `SYSTEM_PROMPT` 규칙 | 지어내기(환각), 확인 없는 주문 | 2, 5 |
| 코드 검증 + 롤백 | AI가 실수해도 데이터가 망가지지 않게 | 7 (2겹) |
| 반복 최대 8번 | 무한 반복, 비용 폭주 | |
| 에러를 결과로 전달 (`is_error`) | 대화가 끊기지 않고 Claude가 상황을 설명 | |

**🟧 ⑤ Tool 정의 (`TOOLS`)**

```python
{
    "name": "search_products",              # Claude가 요청할 때 쓰는 이름
    "description": "원두를 검색합니다. ...",   # Claude가 읽고 언제 쓸지 판단
    "strict": True,                         # 양식을 반드시 지키게
    "input_schema": {...},                  # 입력 양식 (JSON Schema)
}
```

- 실행되는 코드가 아니라 Claude에게 보여주는 **설명서**
- `input_schema` = 메서드의 파라미터 목록. Pydantic 요청 양식과 같은 역할인데, **Claude가 양식을 채움**
- `description`에 따라 Claude의 행동이 달라짐 (시나리오 3)

**🟧 ⑥ Tool 실행 (`run_tool`)**

- Claude는 기능 이름을 **문자열**로 보냄 → 이름 → 함수 연결표(`_HANDLERS`)로 찾아서 실행
- REST API와 Tool이 **같은 서비스 함수를 재사용** → 비즈니스 로직이 한 곳에만 있음
- 에러를 던지지 않고 `is_error: true`로 돌려줌 → Claude가 손님에게 설명하고 대안 제시

**🟧 ⑦ 응답 읽는 법**

| 항목 | 의미 |
|---|---|
| `stop_reason: "tool_use"` | 기능 실행해줘 (최종 답 아님) |
| `stop_reason: "end_turn"` | 최종 답변 |
| 블록 `type: "text"` | Claude가 한 말 |
| 블록 `type: "tool_use"` | 기능 실행 요청서 (`id`, `name`, `input`) |
| `role: "assistant"` | Claude가 보낸 것 |
| `role: "user"` | Claude 바깥에서 보낸 것 (손님 질문, 서버의 실행 결과 `tool_result`) |

**⬜ 몰라도 되는 것**

- `betas`, `fallbacks`, `output_config(effort)` 같은 API 옵션
- `pause_turn`, `refusal` 처리 세부
- `**tool_input`, `json.dumps(ensure_ascii=False)` 같은 문법

## 2. 실행 시나리오

실제 Claude API 키로 서버를 실행하고, Swagger(`/docs`)에서 `POST /chat`을 호출한 결과. 응답 JSON은 핵심 부분만 줄여서 적음.

### 시나리오 1. 7000원 이하 원두 찾기

```json
"tool_calls": [
  {"name": "search_products",
   "input": {"keyword": null, "max_price": 7000, "in_stock_only": true},
   "output": "{\"count\": 3, \"products\": [Columbia Nariño 5000, Brazil 6000, Columbia Quindío 7000]}"}
]
"reply": "7,000원 이하이면서 지금 바로 주문할 수 있는 원두는 3가지예요. ..."
```

- 7,000원 → `max_price = 7000`으로 바꿔서 `search_products` 호출
- 서버 → DB를 검색하여 3가지를 찾음
- Claude → 결과를 보고 정리하여 답변
- 손님이 말하지 않은 `in_stock_only: true`도 "추천이니까 살 수 있는 것만"이라고 Claude가 스스로 판단해서 넣음

⭐ **Tool Use의 기본 동작:** `input_schema`(keyword, max_price, in_stock_only)에 적어둔 양식을 Claude가 읽고 사람의 말을 그 양식에 맞게 채움 = 자연어(7000원 이하)를 Tool의 입력값(`max_price`)으로 바꿈

### 시나리오 2. 가장 인기 있는 원두 찾기

```json
"tool_calls": [
  {"name": "search_products",
   "input": {"keyword": null, "max_price": null, "in_stock_only": true},
   "output": "{\"count\": 4, \"products\": [id, name, price, stock만 있음]}"}
]
"reply": "죄송하지만 저희 시스템에는 판매량이나 인기 순위 정보가 없어서 \"가장 인기 있는 원두\"는 알려드릴 수 없어요. 대신 ..."
```

- `output`에 인기, 판매량 정보가 없다 → reply에서 "판매량이나 인기 순위 정보가 없어서 알려드릴 수 없어요"

⭐ `SYSTEM_PROMPT`에 "추측하지 말고 Tool로 확인하라"는 규칙을 넣었기 때문에 Claude가 지어내지 않고 솔직하게 답변 (환각 방지)

### 시나리오 3. 에티오피아 원두 주문 요청

```json
"tool_calls": [
  {"name": "search_products",
   "input": {"keyword": "에티오피아", "max_price": null, "in_stock_only": false},
   "output": "{\"count\": 0, \"products\": []}"},
  {"name": "search_products",
   "input": {"keyword": "Ethiopia", "max_price": null, "in_stock_only": false},
   "output": "{\"count\": 1, \"products\": [{\"id\": 4, \"name\": \"Ethiopia Sidamo\", \"price\": 8000, \"stock\": 100}]}"}
]
"reply": "에티오피아 원두는 지금 1종 있어요. Ethiopia Sidamo: 8,000원 ..."
```

DB에는 상품 이름이 모두 영어로 되어 있다.

- 한글로 검색하면 서버가 상품을 찾지 못한다 (`WHERE name LIKE '%에티오피아%'`)
- 서버가 count: 0 결과를 Claude에게 돌려주고, **Claude가 그걸 보고 스스로 번역해서** 다시 검색한다
    - 코드에는 번역이나 재검색 로직이 존재하지 않는다 = 반복문이 결과를 다시 Claude에게 보내주기 때문에 가능
- 하지만 Claude 호출 횟수가 1번 늘어서(2번 → 3번) 비용과 응답 시간이 는다 → Tool 설명에 "상품명은 영어"라고 적어주는 것이 좋음

⭐ **결과를 보고 다음 행동을 스스로 바꾼 AI Agent의 대표 장면**

### 시나리오 4. 디테일한 요청 (선물 추천)

```json
{"message": "친구한테 선물하려고 하는 어떤 원두 추천해? 그 친구는 산미가 있는 커피를 좋아해"}
```

```json
"tool_calls": [
  {"name": "search_products",
   "input": {"keyword": null, "max_price": null, "in_stock_only": true},
   "output": "{\"count\": 4, ...}"}
]
"reply": "1. Ethiopia Sidamo (8,000원) 에티오피아 원두는 보통 꽃향과 상큼한 과일 산미로 ...
          2. Columbia Quindío (7,000원) 발효 시간을 늘려 가공한 원두라서 ...
          맛 설명은 원산지와 가공 방식의 일반적인 특징을 바탕으로 한 거예요.
          상품 정보에 맛 노트가 따로 없어서 실제 맛은 조금 다를 수 있어요."
```

- `output`에는 맛 정보가 존재하지 않는다 → Claude가 원래 알고 있는 일반 지식으로 답변
- Tool로 가져온 가게 데이터(가격, 재고)와 LLM의 일반 지식(원산지 특징)을 결합해서 추천
- 시나리오 2(인기 순위는 가게만의 정보라 "모른다")와 달리, 일반 지식으로 답하되 **출처의 한계를 밝힘**

### 시나리오 5. 주문 요청

```json
{"message": "Ethiopia Sidamo 2개 주문할게요. 이메일은 test@test.com 이에요"}
```

```json
"tool_calls": [
  {"name": "search_products",
   "input": {"keyword": "Sidamo", "max_price": null, "in_stock_only": false},
   "output": "{\"count\": 1, \"products\": [{\"id\": 4, \"name\": \"Ethiopia Sidamo\", \"price\": 8000, \"stock\": 100}]}"}
]
"reply": "주문하시기 전에 아래 내용을 확인해 주세요. 이메일: test@test.com / 상품: Ethiopia Sidamo × 2개 / 총액: 16,000원 ... 이대로 주문할까요?"
```

- 주문 정보가 다 있어도 바로 주문하지 않고 총액을 보여주며 확인을 받았다
- `tool_calls`에 `create_order`가 없다 = 실제로 주문하지 않았다는 증거
- `SYSTEM_PROMPT`에 "확인 없이 주문하지 마라"는 규칙이 있었기 때문 (Human-in-the-loop)

### 시나리오 6. 실제 주문 ⭐

**요청**

```json
{
  "message": "네, 주문해주세요",
  "history": [
    {"role": "user", "content": "Ethiopia Sidamo 2개 주문할게요. 이메일은 test@test.com 이에요"},
    {"role": "assistant", "content": "주문하시기 전에 아래 내용을 확인해 주세요. ... 이대로 주문할까요?"}
  ]
}
```

**응답**

```json
"tool_calls": [
  {"name": "search_products",
   "input": {"keyword": "Ethiopia Sidamo", ...},
   "output": "{\"count\": 1, \"products\": [{\"id\": 4, ... \"stock\": 100}]}"},
  {"name": "create_order",
   "input": {"customer_email": "test@test.com", "items": [{"product_id": 4, "quantity": 2}]},
   "output": "{\"message\": \"당일 오후 2시 이후의 주문 건은 다음 날 배송이 시작됩니다.\", \"total_price\": 16000,
              \"orders\": [{\"order_id\": 1, \"order_date\": \"2026-11-18T21:46:46\", \"quantity\": 2,
              \"product\": {\"id\": 4, \"stock\": 98}}]}"}
]
"reply": "주문이 완료됐어요. 주문번호: 1 / 총액: 16,000원 / 오후 2시 이후(21:46)에 주문하셔서 내일 배송이 시작돼요.
          참고로 지난번 답변에서는 가격과 재고를 확인하지 않고 말씀드렸어요. ..."
```

**재고 확인 (`GET /products/4`)** → 실제로 2개가 줄어 있음

```json
{"id": 4, "name": "Ethiopia Sidamo", "price": 8000, "stock": 98}
```

- 서버는 대화를 저장하지 않기 때문에, "네, 주문해주세요"만 보내면 Claude는 무엇을 주문하라는 건지 알 수 없다 = 이전 대화를 `history`에 담아 보낸 이유
- 주문을 위해 상품 id를 검색 → 2개 주문 = 대화 앞부분의 정보(이메일, 수량) + 방금 받은 검색 결과(id=4)를 조합하여 주문 값을 생성
- 손님의 말 한마디 → Claude의 판단 → 서비스 함수 실행 → **실제 DB 변경**까지 확인

🚨 **문제 발견 (구조의 한계)**

1. `history`에 텍스트만 넣어서 Claude가 이전에 검색한 기록을 볼 수 없었다 → "가격과 재고를 확인하지 않고 말했다"고 사실과 다르게 판단
2. 주문할 때 상품 id가 필요한데, 시나리오 5의 답변(텍스트)에는 상품 id가 없어서 다시 검색할 수밖에 없었다

이 때문에 검색을 한 번 더 하게 되고(비용, 시간 증가), 잘못된 안내로 서비스에 대한 신뢰가 떨어질 수 있다.

```text
시나리오 5에서 실제로 오간 대화          history로 넘어간 것
user:      "2개 주문할게요..."          user:      "2개 주문할게요..."
assistant: [검색 요청: Sidamo]          (빠짐)
user:      [검색 결과: id=4, 8000원]     (빠짐)
assistant: "확인해 주세요..."           assistant: "확인해 주세요..."
```

✍️ **개선 방안**

현재 구조는 같은 대화에서 지금까지 오간 말을 전부, 순서대로 `history`에 넣어야 한다. 이때 `history`는 텍스트만 받는다. 따라서 맥락을 빠짐없이 전달하려면 **Tool 기록(Claude가 한 말의 근거 자료)까지 포함한 대화 전체**를 저장하거나 주고받는 구조가 필요하다.

1. 서버가 대화 전체(`messages`)를 저장 → 프론트엔드는 `history` 대신 대화 ID만 보낸다
    - `reply`만 저장하면 Tool 기록은 저장되지 않는다
    - 마지막 답변도 `messages`에 붙여서 저장해야 한다
    - 함께 고민할 것: 대화가 길어질 때의 비용, 저장 기간(TTL), 다른 사람의 대화 ID로 접근하는 문제(인증)
2. 응답에 Tool 기록까지 포함한 대화 전체를 담아 돌려주고, 다음 요청 때 그대로 다시 보내기

참고: 주문처럼 되돌리기 어려운 작업 직전에 최신 재고를 다시 확인하는 것 자체는 좋은 습관일 수 있다. 문제는 재검색이 아니라 "확인하지 않았다"는 잘못된 안내.

⭐ **LLM에게 판단에 필요한 맥락을 빠짐없이 전달해야 한다**

### 시나리오 7. 재고보다 많이 주문하기

```json
{"message": "Brazil Serra Do Caparaó 500개 주문할게요. 이메일은 test@test.com 이에요"}
```

```json
"tool_calls": [
  {"name": "search_products",
   "input": {"keyword": "Brazil", ...},
   "output": "{\"count\": 1, \"products\": [{\"id\": 2, \"name\": \"Brazil Serra Do Caparaó\", \"price\": 6000, \"stock\": 100}]}"}
]
"reply": "재고가 100개뿐이에요. 500개는 한 번에 주문할 수 없어요.
          1. 재고 100개만 주문 (총액 600,000원)  2. 부족한 400개는 다른 원두로 채우기 ..."
```

- 재고 처리 장치 두 겹
    - **1겹 (이번에 동작함):** Claude가 검색 결과(재고 100개)를 보고 미리 판단 → 주문을 시도하지 않고 대안을 제시
    - **2겹 (이번엔 실행 안 됨):** 만약 주문을 시도했다면 `order_service`가 재고 부족 에러 → 롤백 → Claude에게 `is_error: true`로 전달. 테스트 코드(`test_chat_tool_error_is_returned_to_claude`)로 검증
- 두 겹이 필요한 이유: AI의 판단에만 의존하지 않고 코드 레벨의 검증을 함께 둔 것

### 시나리오별 Agent다운 장면

| 시나리오 | 확인한 것 | 핵심 키워드 |
|---|---|---|
| 1 | 자연어를 Tool 입력값으로 변환 | Tool Use 기본 |
| 2 | 없는 정보를 지어내지 않음 | 환각 방지 |
| 3 | 실패한 검색을 스스로 복구 | 결과를 보고 행동을 바꿈 |
| 4 | 가게 데이터 + 일반 지식 결합, 한계를 밝힘 | RAG 필요성 |
| 5 | 행동할 수 있어도 멈추고 확인 요청 | Human-in-the-loop |
| 6 | 검색 → 주문 → 실제 DB 변경, history 한계 발견 | 핵심 증거 + 맥락 관리 |
| 7 | 재고를 미리 확인해서 계획을 바꿈 | 이중 안전장치 |

### API 실행하면서 느낀 점

1. **SYSTEM_PROMPT 규칙의 중요성:** 데이터의 정확성과 신뢰를 위해서는 올바른 규칙을 세우는 것이 중요하다는 걸 느꼈다. (시나리오 2: 판매량을 지어내지 않음 / 시나리오 5: 주문 전 확인)
2. **검색 이름 불일치 대비:** 당장은 Tool 설명에 "상품명은 영어"라고 적어 개선할 수 있고, 근본적으로는 한글 이름 컬럼을 추가해 둘 다 검색되게 하는 방식을 고려해봐야겠다. (시나리오 3)
3. **가게 데이터와 일반 지식의 구분:** 맛 정보가 없어 답을 못 할 거라 예상했는데, Claude가 Tool로 가져온 가게 데이터와 자신이 가진 일반 지식을 결합해서 산미 있는 원두를 추천했다. 모든 정보를 DB에 일일이 저장하지 않아도 두 정보를 함께 활용할 수 있다는 점이 AI Agent의 큰 장점으로 와닿았다. 하지만 틀린 정보를 말하는 것을 막으려면 지금처럼 가격과 재고같이 틀리면 안 되는 정보는 반드시 Tool로 조회하게 하고, 일반 지식으로 답할 때는 한계를 밝히는 것을 규칙으로 명시해야 할 것 같다. (지금은 Claude가 스스로 판단하여 한계를 밝혔던 것) (시나리오 4)
4. **맥락은 빠짐없이:** LLM은 이전 대화를 기억하지 못하고 전달받은 정보만으로 판단한다. 따라서 판단에 필요한 맥락과 Tool 기록까지 빠짐없이 전달하지 않으면 같은 검색을 반복해 비용과 시간이 늘고, 사실과 다른 안내로 신뢰가 떨어질 수 있다. (시나리오 6)
5. **AI에만 의존하지 않는 설계:** AI 판단에만 의존하지 않도록 안전장치를 겹겹이 두는 설계가 필요하다. 규칙이 명확한 건 코드로 한 번 더 검증하고(시나리오 7: 재고 검증과 롤백), 되돌리기 어려운 작업은 사람의 확인을 받아야 한다(시나리오 5: 주문 전 확인).

### 프로젝트 소개

**Q. 이 프로젝트를 소개해 주세요.** (1분 버전 연습)

> 데브코스에서 팀으로 만든 Spring Boot 원두 주문 서비스를 FastAPI로 옮기고, Claude API의 Tool Use를 연결해서 자연어로 원두 검색부터 주문까지 처리하는 AI Agent를 만들었습니다. 기존 서비스 함수(검색, 주문, 주문 조회)를 Tool로 등록해 Claude가 손님의 요청을 보고 필요한 Tool을 스스로 골라 호출하게 했습니다. 실제 API로 여러 시나리오를 실행해 보면서 대화 기록에서 Tool 기록이 빠지는 구조적 한계를 발견했고, 개선 방향도 정리했습니다.

**Q. 왜 FastAPI로 옮겼어요?**

💡 AI 생태계 / API 중심 / 타입 기반 자동 검증과 문서

> AI 관련 SDK와 라이브러리가 Python에 가장 풍부해서 AI 기능을 붙이고 실험하기 유리하다고 판단했습니다. 그중 FastAPI는 API 서버에 특화되어 있고, 타입 선언만으로 요청 검증과 API 문서가 자동으로 생겨서 Spring의 DTO와 Swagger에 익숙한 저에게 전환이 쉬웠습니다.

⚠️ "Python으로만 AI를 쓸 수 있다"고 말하지 않기. Claude API는 Java SDK도 있어요.

**Q. Django나 Flask도 있는데 왜 FastAPI예요?**

| | FastAPI | Django | Flask |
|---|---|---|---|
| 성격 | API 서버에 특화, 가벼움 | 다 갖춘 종합 세트 (ORM, 관리자, 로그인) | 최소한만 있음 |
| 이 프로젝트에 | ✅ 화면 없이 API만 필요 | 과함 | 검증, 문서를 직접 붙여야 함 |

> 이번엔 화면 없이 API만 필요했고, Django는 기능이 많아 과했고 Flask는 검증과 문서를 직접 붙여야 해서, API 개발에 필요한 걸 기본으로 갖춘 FastAPI를 골랐습니다.

**Q. 코드는 직접 다 짜셨어요?**

솔직하게 답하는 게 가장 안전해요.

> AI 코딩 도구를 활용해서 구현했고, 생성된 코드를 Spring과 비교하며 한 줄씩 분석했습니다. 그다음 실제 API로 시나리오를 직접 실행하면서 문제를 발견하고 개선 방향을 정리했습니다.

### FastAPI

**Q. Spring Boot와 FastAPI는 뭐가 달라요?**

💡 의존성 주입 / 트랜잭션 / 검증

> 구조는 같고, 세 가지가 달랐습니다. 의존성 주입은 Spring이 시작할 때 Bean으로 주입하는 반면 FastAPI는 요청마다 `Depends`로 주입합니다. 트랜잭션은 Spring의 `@Transactional`과 달리 commit과 rollback을 직접 써야 했습니다. 검증은 `@Valid` 없이 Pydantic 타입 선언만으로 자동으로 됩니다.

**Q. FastAPI에서 트랜잭션은 어떻게 처리했어요?**

💡 try / commit / except / rollback

> 요청마다 세션을 하나 열고, 주문 작업을 모두 마친 뒤 commit하고, 중간에 에러가 나면 rollback하도록 직접 작성했습니다.

**Q. 기존 Spring 코드에서 개선한 점은요?**

💡 상품마다 트랜잭션 → 일부만 주문 → 하나로 묶어 전부 롤백

> 기존엔 주문 상품마다 트랜잭션을 따로 열어서, 여러 상품 중 하나가 재고 부족이면 일부만 주문되는 문제가 있었습니다. 주문 전체를 하나의 트랜잭션으로 묶어서 하나라도 실패하면 전부 롤백되게 했고, 테스트로 확인했습니다.

**Q. 세션은 어떻게 관리했어요?**

💡 영속성 컨텍스트 / 요청마다 하나 / Depends + yield

> SQLAlchemy 세션은 JPA의 영속성 컨텍스트와 같은 역할입니다. `Depends`와 `yield`로 요청이 오면 세션을 열고, 응답 후 반드시 닫도록 해서 요청끼리 데이터가 섞이지 않게 했습니다.

**Q. FastAPI는 비동기가 장점이라던데 써봤어요?**

> FastAPI가 비동기를 지원하는 건 알지만, 이번엔 이해를 우선해서 동기 방식으로 구현했습니다. Claude API 호출처럼 기다리는 시간이 긴 작업이 많아지면 비동기로 바꾸는 게 다음 단계라고 생각합니다.

**Q. 동시에 같은 원두를 주문하면요?**

💡 동시성 / 락

> 두 사람이 동시에 마지막 재고를 주문하면 둘 다 성공할 수 있는 한계가 있습니다. 조회할 때 잠금을 거는 비관적 락이나, 버전 컬럼으로 충돌을 감지하는 낙관적 락으로 해결할 수 있습니다.

### Claude Tool Use / AI Agent

**Q. Tool Use가 뭐예요?**

💡 Claude는 요청만 / 실행은 서버 / stop_reason

> Claude에게 사용할 수 있는 기능 목록을 알려주면, Claude가 필요한 기능과 입력값을 골라서 실행을 요청합니다. 실제 실행은 우리 서버가 하고, 결과를 다시 Claude에게 돌려줍니다. Claude는 DB에 직접 접근하지 않습니다.

**Q. AI Agent가 뭐예요? 챗봇이랑 뭐가 달라요?**

💡 실제로 일을 처리 / 결과를 보고 다음 행동 결정

> 챗봇은 말로 답하고 끝나지만, Agent는 Tool로 실제 일을 하고 그 결과를 보고 다음 행동을 스스로 정합니다. 제 프로젝트에서도 '검색 → 주문' 순서를 코드로 정하지 않았는데, Claude가 판단해서 검색 후 주문까지 처리했고 실제 DB 재고가 줄었습니다.

**Q. Claude는 이전 대화를 기억하나요?**

💡 stateless / 매번 대화 전체 전송 → 시나리오 6으로 연결

> 기억하지 못합니다. 그래서 매번 대화 전체를 다시 보내야 하는데, 이 부분에서 실제로 문제를 발견했습니다. (→ 아래 "발견한 문제" 답변으로 이어가기)

**Q. Claude는 어떤 Tool을 쓸지 어떻게 알아요?**

💡 description / input_schema

> Tool마다 이름, 설명, 입력 양식을 정의해서 보냅니다. Claude는 설명을 읽고 언제 쓸지 판단하고, 입력 양식에 맞춰 값을 채웁니다. 실제로 설명 한 줄에 따라 Claude의 행동이 달라지는 걸 확인했습니다.

**Q. 왜 기존 서비스 함수를 Tool로 썼어요?**

💡 로직 재사용

> REST API와 Claude가 같은 서비스 함수를 쓰게 해서, 재고 차감 같은 비즈니스 로직이 한 곳에만 있도록 했습니다.

**Q. AI가 잘못 주문하면 어떻게 해요?**

💡 안전장치 3겹

> 첫째, 시스템 프롬프트로 주문 전에 손님 확인을 받게 했습니다. 둘째, 재고 부족처럼 규칙이 명확한 건 코드에서 검증하고 실패하면 롤백합니다. 셋째, 무한 반복을 막으려고 Claude 호출을 최대 8번으로 제한했습니다. 실제 실행에서 주문 전에 확인을 받는 것과, 재고를 넘는 주문을 미리 막는 걸 확인했습니다.

**Q. Tool 실행 중 에러가 나면요?**

💡 is_error로 Claude에게 전달

> 에러를 서버에서 던지지 않고 Claude에게 결과로 돌려줍니다. 그래야 Claude가 손님에게 "재고가 부족해요, 100개만 주문할까요?"처럼 설명하고 대안을 제시할 수 있습니다.

**Q. LLM이 틀린 정보를 말하면요?**

💡 틀리면 안 되는 정보는 Tool로 / 일반 지식은 한계를 밝히기

> 가격과 재고처럼 틀리면 안 되는 정보는 반드시 DB에서 Tool로 조회하도록 규칙을 정했습니다. 일반 지식으로 답할 때는 한계를 밝히게 하고, 더 정확한 정보가 필요하면 관련 문서를 함께 제공하는 방식으로 보완할 수 있습니다.

**Q. 테스트는 어떻게 했어요?**

💡 가짜 Claude / 비용 없이 반복문 검증

> Claude 클라이언트를 `Depends`로 주입받게 해서, 테스트에서는 정해진 대본대로 답하는 가짜 Claude로 바꿔 끼웠습니다. API 비용 없이 반복문이 Tool을 실행하고 결과를 돌려주는지 검증했습니다.

### 문제 해결 ⭐ 가장 중요

**Q. 어려웠던 점이나 발견한 문제가 있었나요?**

시나리오 6으로 답하기. 이 순서대로 말하면 돼요.

1. **상황:** 주문 확인 후 "네"라고 하자 주문은 됐는데, Claude가 "이전엔 가격을 확인하지 않았다"고 사실과 다르게 안내함
2. **원인:** 대화 기록을 텍스트로만 넘겨서 이전 검색 기록(Tool 기록)이 빠짐. 상품 id도 텍스트에 없어서 다시 검색함
3. **영향:** 불필요한 재검색(비용, 시간) + 잘못된 안내(신뢰 저하)
4. **배운 점:** LLM은 전달받은 정보만으로 판단하므로, Tool 기록까지 맥락을 빠짐없이 전달해야 함
5. **개선:** 서버가 Tool 기록을 포함한 대화 전체(`messages`)를 저장하고, 대화 ID로 이어가는 구조

**Q. AI가 예상 밖으로 행동한 적은요?**

시나리오 3으로 답하기.

> 한글로 검색해서 0개가 나왔는데, Claude가 결과를 보고 스스로 영어로 다시 검색해서 찾았습니다. Agent의 장점을 확인했지만 호출이 한 번 늘어서, Tool 설명에 "상품명은 영어"라고 명시하는 개선 방법을 찾았습니다.

**Q. 실제로 실행해 보니 어땠어요?**

느낀 점 3번(시나리오 4)으로 답하기.

> 맛 정보를 DB에 저장하지 않아서 추천이 어려울 거라 예상했는데, Claude가 Tool로 가져온 가격과 재고에 자신의 일반 지식을 결합해서 산미 있는 원두를 추천했습니다. 동시에 "실제 맛은 다를 수 있다"고 한계를 밝히는 걸 보면서, 틀리면 안 되는 정보는 반드시 Tool로 가져와야 한다는 것도 배웠습니다.

### 한계와 개선

**Q. 더 개선한다면요?**

2~3개만 골라서 말하기.

- Tool 기록을 포함한 대화 저장 (시나리오 6)
- **인증 연동:** 지금은 손님이 말한 이메일로 주문해서 남의 이메일로도 주문 가능 → 로그인 정보에서 이메일을 가져와야 함
- Tool 설명 개선, 한글 상품명 컬럼 추가 (시나리오 3)
- 동시 주문 시 재고 문제 → 락
